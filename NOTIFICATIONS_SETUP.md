# Notification platform — setup guide

Everything you asked for is now built and typechecked. This file is the only
thing left between you and it working: run one SQL file in Supabase, paste
three values into your env file, and deploy on HTTPS. No Firebase anywhere.

---

## 1. Run the migration in Supabase (2 minutes)

Run the migrations in numeric order. For an existing installation that has
already applied 0018, the mobile reliability addition is:

```
supabase/migrations/0042_push_delivery_health.sql
```

New installations must still run `0018_notification_platform.sql` first.

Open it and run it **in the SQL editor** of your Supabase project (the same
place you ran 0001–0017). It is idempotent — if it fails halfway, fix the
reason and re-run the whole thing.

What it adds:

| Piece | Why |
|---|---|
| `push_subscriptions` table | Stores each browser's push endpoint + keys. RLS on, no policies (server-only, like your prefs tables). |
| RLS policy on `notifications` | **The security-critical one.** The bell and the realtime feed read from the browser with the publishable key, so this policy is what stops one user from reading another's notifications: `profile_id = current_profile_id()`. |
| `notification_preferences.push` column | Per-event push channel for managers (next to `in_app`/`email`). Defaults to `true`. |
| `customer_preferences.push_enabled` column | One master push switch per customer. Defaults to `true`. |
| `notification_sound` + `push_enabled` settings | `notification_sound` is the platform-wide sound (admin picks it on `/a/settings` → Notifications). `push_enabled` is the master switch for web push. |
| `notifications` in the `supabase_realtime` publication | The database half of realtime. The browser already ships the Supabase client; this is what lets it subscribe. |

At the end the file runs 5 verification queries. You want all of them to
return rows — if any comes back empty, that piece did not apply.

**Optional but recommended:** in the Supabase dashboard go to
**Database → Replication** and confirm `notifications` is ticked under
`supabase_realtime` (the migration does this for you, but seeing it there
confirms it).

## 2. The VAPID keys — already generated for you

One VAPID keypair works for **both Chrome and Edge** (it also covers
Firefox, Opera and Samsung Internet — they all speak the same Web Push
protocol; the keys are not per-browser).

I generated a real keypair and wrote it into your `.env.local` under:

```
VAPID_PUBLIC_KEY=...
VAPID_PRIVATE_KEY=...
VAPID_SUBJECT=mailto:you@your-domain.com
```

`VAPID_SUBJECT` is the one line you should edit — it's just a contact
address the push service can reach you at (an email or `https://…` URL).

`.env.example` has the same three keys with `REPLACE_ME` placeholders so
other environments (staging/production) get the same setup:

```
VAPID_PUBLIC_KEY=REPLACE_ME
VAPID_PRIVATE_KEY=REPLACE_ME
VAPID_SUBJECT=mailto:REPLACE_ME
```

### If you deploy elsewhere

Generate a fresh keypair for production (never share the private key):

```bash
npx web-push generate-vapid-keys --json
```

…then put the three values into the production env vars. The public key
**must** be available to the browser too, as `NEXT_PUBLIC_VAPID_PUBLIC_KEY`
(that one is public by design — the browser needs it to subscribe).

## 3. HTTPS — the one hard requirement

Web Push **only works over HTTPS** (or `localhost`). If you test this on a
plain-http URL, the browser will refuse to subscribe — that's a browser
rule, not a bug in the code.

- **On your deployed URL** — you're fine if you have an HTTPS certificate.
- **iOS Safari** — Web Push only works from **iOS 16.4+**, and only when the
  site is **installed to the home screen** (added as a PWA). In a normal
  Safari tab it will not work. This is Apple's rule.
- **Android Chrome / Edge / desktop Chrome / desktop Edge** — works out of
  the box. Given your audience is mainly Android, this is the platform that
  matters.

## 4. What you should see, feature by feature

### The bell + unread badge (all three shells)

- Manager: top bar of `/m/*`
- Admin: top bar of `/a/*`
- Customer: header of the public site (signed in)

The badge shows live unread count. Click → dropdown of the latest
notifications → tap one to deep-link to the order/reservation/review →
"Mark all read". Unread rows are highlighted.

### Realtime + sound (tab open)

With the app open in a tab, trigger an event (below). Within a second or
two: the badge bumps instantly, a toast pops, and the notification sound
plays — once the page has been clicked at least once (browsers block audio
until then, and there's nothing to announce to an untouched tab anyway).

**The sound.** The admin picks it on `/a/settings` → **Notifications**.
Six sounds ship in `public/sounds/` (`chime`, `ding`, `pop`, `triple`,
`alert`, `tri-tone` — an iPhone-style three-note chime), generated by
`scripts/generate-sounds.mjs` (run `node scripts/generate-sounds.mjs` to
regenerate).

### Count badges in the sidebar + dashboard attention

- Manager sidebar: **Orders** shows how many orders need action, **Réservations** how many are pending.
- `/m` dashboard: a "Requires your attention" panel with links to orders, reservations, low stock, and unreplied reviews.
- The mobile tab bar's Orders tab shows the live count too.

### Install + notification banners (PWA)

The site is a real PWA: manifest, icons, standalone display and a service
worker. On every page load the app **checks** two things automatically —
is the site installed, and has the browser decided on notification
permission — and offers a small bottom banner for whatever is missing:

- **Not installed** → an "Install" banner (Chrome/Edge use the browser's
  install prompt; on iPhone/iPad it shows the "Add to Home Screen" steps,
  which is also what unlocks iOS web push).
- **Signed in + notifications undecided** → an "Enable notifications"
  banner that asks the browser for permission and subscribes the device
  right there.

Tap **Later** (or the ✕) and that banner stays quiet for **one hour**
(stored in `localStorage`), then offers again. Accepting is remembered
forever — an installed app or granted permission is never asked again.
On iPhone/iPad the notification banner is deliberately withheld until the
Home Screen app is installed; Safari tabs cannot receive iOS Web Push.

### Web push (tab closed / phone)

On the settings page (manager: `/m/settings`, customer: `/settings`) there's
a **"Notifications on this device"** toggle. Tap it → browser asks
permission → allow → the device is subscribed. Close the tab: the next
notification still arrives as an OS-level notification, and tapping it opens
the right page. Unsubscribing deletes the server's copy. Every app open also
repairs a missing endpoint and replaces subscriptions created with an older
VAPID key.

### Email

Every event also emails people who have that channel on, through the
existing `trySendMail`/SMTP. Broadcasts now email too, when the admin ticks
"also send by email" in the composer.

### Triggers now wired (the endpoints that notify)

| Event | Trigger | Recipient |
|---|---|---|
| `new_order` | online checkout, waiter table order | branch staff |
| `order_status` | order advanced (incl. delivery fee quoted) | customer |
| `order_cancelled` | cancelled by either side | other side |
| `low_stock` | a tracked dish crosses its threshold | branch staff |
| `loyalty` | points earned on delivery | customer |
| `reservation` | new reservation request | branch staff |
| `reservation_decision` | confirmed / declined | customer |
| `review` | new customer review | branch staff |
| `review_reply` | restaurant replies | customer |
| `moderation` | review reported | admins |
| `billing` / `billing_paid` / `billing_refund` | plan change, invoice paid, refund | manager |
| `approval` | restaurant approved / suspended / reinstated | owner |
| `account` | user suspended / reinstated (allowed even while suspended) | user |
| `new_subscription` | tenant picks a plan / starts a trial | admins |
| `support` | contact form message | admins |
| `broadcast` | admin broadcast (now with email + push) | audience |

Each delivery is gated by the recipient's own preferences (which already
existed and persist) plus the new push channel. A missing preference row
means "on by default", never "silently off".

## 5. Testing checklist (do this in order)

1. **Migrate** — run 0018 for a new project and 0042 for mobile delivery
   health; watch their verification queries return rows.
2. **Restart the dev server** — so `.env.local`'s VAPID keys load.
3. **Login as a manager**, place an order as a customer in another browser:
   badge bumps, toast appears, sound plays, email arrives (if SMTP is on).
4. **Sidebar badge** — confirm Orders count matches the dashboard.
5. **Push** — on `/m/settings` (HTTPS or localhost), toggle the device on,
   use **Send a test notification** once, then close the installed app/tab and
   trigger the test from another signed-in device. Expect an OS notification.
6. **Admin sound** — `/a/settings` → Notifications, pick a different sound,
   order again, hear the new one.
7. **Broadcast** — send one to managers; check bell, email (if ticked) and
   push arrive on a signed-out tab.

## 6. Notes

- **Cost**: zero. Web Push flows through the browser vendors' own push
  services; no Firebase, no subscription. Supabase Realtime stays within its
  free tier for hundreds of concurrent users.
- **The 4 pre-existing tables that had RLS on but no policies** (from my
  earlier analysis) were `notifications`, `broadcasts`,
  `notification_preferences`, `customer_preferences`. Only `notifications`
  needed a client policy — the bell reads it from the browser. The other
  three stay server-only, which is the safe default.
- If you later want to regenerate the sounds (different tone/volume), edit
  `scripts/generate-sounds.mjs` and re-run `node scripts/generate-sounds.mjs`.
- An HTTP 201/accepted result means the browser vendor accepted the message;
  it does not prove the handset displayed it. If Android accepts but displays
  nothing, check the site's notification category and battery/background
  restrictions. If the service returns 404/410, the app removes that expired
  subscription automatically. A 401/403 usually means a VAPID mismatch; open
  the app once and the subscription repair will replace the stale endpoint.
